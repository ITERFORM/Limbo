# W3 tape: checkpoints, rewind and homes (2026-11-20)

PLAN.md 3.4: the conversation is a tape, appended in place; a turn must not re-read what the engine already read. Qwen3.6's template drops the
reasoning of every assistant turn before the last user query, so each new user turn diverges inside the tape and `limbo_serve_gpu` re-read
everything (bench/serve-gpu-2026-11-19.md: 3,992 tokens, 0 cached). This file records the fix: recurrent-state snapshots in VRAM, a rewind that
copies no K/V, checkpoints at every message boundary, and a second home for side calls. Everything below was run on 2026-11-20 on the desktop
(RTX 4060 Ti 16 GB, rung 1 = Qwen3.6-35B-A3B UD-IQ3_XXS) under `flock build/gpu.lock`, built with `make BUILD=build-tape`.

## 1. The Gpu state API (`include/limbo/cuda/gpu.hpp`, `src/cuda/gpu_state.cu`)

What a conversation is on this model: K/V on the 10 full-attention layers (positional: the row of position p depends on tokens 0..p and is
written by whichever pass reads p), and on the 30 delta-net layers a recurrent state S (32 heads x 128 x 128 fp32) plus a 3-row conv history of
8,192 floats. The recurrent part folds the whole past into one value: it cannot be rewound, only restored. K/V needs no copy.

| call | what |
|---|---|
| `snapshot_bytes()` | 65,863,680 bytes = 62.81 MiB = 30 x (2,097,152 S + 98,304 conv history) |
| `set_snapshot_slots(want, keep_free_bytes)` / `snapshot_slots()` | K preallocated VRAM slots, one cudaMalloc each; stops at the first failure or when less than `keep_free_bytes` would stay free; returns how many exist |
| `snapshot(slot)` | slot := the live home's recurrent state, as of every pass queued so far (device-to-device copies on the engine's stream: no sync) |
| `restore(slot)` | the live home's recurrent state := slot. The next pass must be at the position the snapshot was taken at |
| `set_homes(n, keep_free)` / `homes()` / `select_home(h)` / `home()` | a home is one conversation (K/V + recurrent state); switching swaps pointers, no copy; the captured decode graphs travel with their home (a graph bakes the state pointers in) |
| `home_bytes()` / `state_vram_bytes()` | 72.8 MiB per extra home at `n_ctx` 512 (K/V is 20 KiB per token: +80 MiB at 4,096); the snapshot slots and extra homes together |

The reconstruction rule: **state at position p = `restore`(the snapshot taken at p), then `prefill`(tokens[p..])**. The K/V rows past p are
overwritten as they are read, and nothing attends past the position it is at.

How to read it: a run of 160 random tokens (prefill in three calls, a step with logits, 8 greedy decode steps) is the reference. Taking snapshots
inside it changes nothing. Running a different branch B over the same positions (stale K/V rows, another recurrent state, prefill and decode),
then `restore` and re-prefilling A's tokens reproduces the reference **bit for bit**, logits of 9 positions included; the control that skips the
restore is off by 1.34 in max|dlogit|, so the test can fail. The batched prefill is chunk-composition invariant (one call or split at 48 and 96:
bit-identical), but a piece shorter than 8 tokens runs the token-by-token path and moves the logits by 9e-5 (this is why serve does not cut a prompt
into tiny pieces for checkpoints that nobody will use, section 2).

## 2. The server: checkpoints at message boundaries (`include/limbo/serve.hpp`, `src/serve.cpp`)

Backend hooks (defaults: unsupported, which keeps the old behaviour, a mismatch resets): `set_snapshot_slots(n)`, `snapshot_slots()`,
`snapshot(slot)`, `restore(slot)`, `prefill_batch_min()`, `set_homes(n)`, `homes()`, `select_home(h)`. `GpuBackend` forwards them to the Gpu API
and keeps 384 MiB free on the card (`kKeepFreeBytes`); `RefBackend` (CPU) has none.

What the server does with them (`Service`):

- **Taking.** While it reads a prompt it cuts the read at message boundaries (the token `<|im_start|>`, past position 0) and calls `snapshot`
  there. Three kinds: **Head** = the generation prompt of a user turn (the last boundary when the last message's role is `user`): the place where
  the next user turn's re-render diverges; **Root** = the first boundary after position 0 (the end of the system prompt and tools): a new
  conversation with the same system prompt restores it; **Plain** = every other boundary. A cut splits one batched pass into two, and every pass
  reads the weights again, so a Plain or Root boundary is skipped when it would leave a piece shorter than `--checkpoint-gap` (default 64 tokens)
  on either side, and no piece is ever cut shorter than the backend's batch minimum (8 on the GPU: a shorter piece runs token by token, slower
  and with other rounding), except the Head's tail. Tool-result turns therefore take no extra cut:
  `cached 1,938 / re-read 29` in 0.065 s (0.070 s before).
- **Keeping.** `--checkpoints N` slots (default 8, 502 MiB on rung 1). When full, the oldest Plain goes first, then the oldest Head but the newest,
  never the Root; a side session only takes another session's slot when it has none to give.
- **Restoring.** A new prompt is compared with the session's tape. If the tape is a prefix: continue (as before). Otherwise `d = min(common prefix,
  prompt - 1)`; the newest checkpoint with position <= d is restored, the tape is cut to that position, the checkpoints past it are released, and
  the read continues from there (`cached_tokens` = that position). No checkpoint at or before `d`, or a refused restore: reset and read everything.
  K/V is never copied, shifted or edited. A repeated request (a prompt shorter than the tape) restores its own generation prompt.
- **`"cache_prompt": false`** (llama-server's field) forces a reset and a cold read; it is what the exactness runs below use.
- **Sessions.** (Replaced in section 8.) `--sessions N` asked the backend for N homes and the header `X-Limbo-Session: <name>` named a
  conversation, none or `main` being session 0.

`serve_test` (CPU, a fake whose state is a hash chain over every consumed token, per home, snapshotted into slots): after every request the live
home's chain is compared with the chain of a cold read of that conversation. 27 new checks: turn 1 takes checkpoints; a tool-result turn restores
nothing; a new user turn restores exactly turn 1's generation prompt and feeds the backend only `prompt - head + generated` tokens, with the state
equal to a cold read; a repeat; `cache_prompt: false`; an edit in the first message restores the Root; an edit inside the tools block is a cold read;
a refused restore falls back to a reset; never more checkpoints than slots; a side call in home 1 leaves main's tape and state untouched; no free
home shares main's; no piece shorter than the batch minimum. A mutation that skips the restore (keeps the position, never calls `restore`) fails 7 of the suite's checks.

(a) The T replay ran after the A replay in the same server: its first request shares A's system prompt and user message and differs only in the
generation prompt (thinking on), so A's turn-1 Head checkpoint (position 1,899) served it. Run alone, a conversation's first request reads cold.

New user turns: **4,003 -> 2,104, 5,078 -> 1,082, 4,095 -> 2,196, 5,164 -> 1,074 tokens re-read**; **2.122 -> 1.256 s, 2.744 -> 0.693 s, 2.161 -> 1.309 s,
2.807 -> 0.684 s** of prefill. The re-read is "from the first re-rendered assistant message after the previous user message to the end" and that is
the floor for any checkpointing: the recurrent state after the divergence depends on everything before it, so the previous turn's tool calls, tool
results (request 3's 1,623 new tokens, almost all a `read_file` result, are in request 4's span) and answer, plus the new user message, are read again. The target "only the
re-rendered last assistant turn plus the new user message" holds for chats without a tool round (one assistant message after the last user
message); with a tool loop it is the whole loop. The zero-cost alternative is the template's own switch: `preserve_thinking: true` keeps the
reasoning in the history, the prompt stays append-only and the tape continues (measured 2026-11-19, `bench/serve-gpu-2026-11-19.md`: 3,977 of
4,004 cached).

Exactness. 12 requests, each compared (the `content`, `reasoning_content` and tool calls of the answer) with the same request read cold:

- the four restored requests (A4, A6, T4, T6) are **identical** to their cold re-reads, and so are the other seven continuations and first requests;
- **T3 differs** from its cold re-read (728 tokens generated cold, 665 on the checkpoint server). It is a plain tape continuation (no restore: the
  tape is a prefix), 665 tokens of greedy thinking over 204 tokens of K/V rows that decode wrote and the cold read computes by prefill (the two
  paths round differently, 9e-5 in `cuda_state_test`'s tail-piece measurement), and the old server's T3 differs from the cold read as well (672
  tokens): three different outputs of the same request, so this is the decode-vs-prefill rounding of any tape, not the restore (the restore itself is
  bit-exact, section 1);
- the old server's outputs equal the new server's for 11 of the 12 requests (T3 again).

Cost of the cuts. A cold read of 4,000 to 5,000 tokens with the checkpoint cuts is 6 to 8 percent slower than the old read in pieces of 1,024
(4,003 tokens 2.257 s against 2.122 s; 5,078 tokens 2.965 s against 2.744 s; T: 2.291 against 2.161 s, 2.969 against 2.807 s); the 1,906-token first
request is within noise (1.082 s after, 1.032 s cold with cuts, 1.064 s before). Requests that continue the tape pay nothing (`re-read 29`: 0.065 s
against 0.070 s).

## 7. Open

- The floor stays: after a divergence everything after it is read again (recurrent state). With tool loops that is the whole previous turn; the
  harness-side fix is `preserve_thinking: true`, or the server could default it for this template (a policy decision, not made here).
- Opening checkpoints inside the system prompt (kindi's dense checkpoints every 256 tokens) are not taken: a changed date or folder in the middle of
  the system block restores nothing and reads cold. Only message boundaries are checkpointed.
- Checkpoints live in VRAM only: no preemptible host copy, nothing on disk, so a restart starts cold (PLAN 3.4 asks for both).
- `Gpu::prefill` runs pieces under 8 tokens token by token (gpu_prefill.cu, not mine) and the Head's tail is 5 to 7 tokens: a user-turn request
  that restores a checkpoint reads 33 tokens in 0.128 s (`Amix 1`, Root restore plus the Head cut) against 29 tokens in 0.065 s for a plain
  continuation, about 0.06 s of cuts and tail that were not separated further. A batched path from 2 tokens would shrink the tail's share, and
  `prefill_batch_min()` in `backend.hpp` would drop to match.
- Homes switch per request; the server is serial, so a second conversation's request waits for the running one to finish (PLAN 3.4's prefill
  share is not needed yet).
- The home swap relies on the decode graphs being `Impl::gexec[2]` / `warm[2]` and on state pointers baked into the capture; a change in how decode
  captures its graphs (per window size, T = 1..8) has to keep them per home. `n_ctx` is still capped at 8,192 by `Gpu::open`.

## 8. Two homes by default, routed by prefix (follow-up, 2026-11-20)

The operator's rule: two conversations are the default, when they fit, because that room is what the engine is for. Changed: the homes are peers
(no main, no side anywhere in the code), `--sessions` defaults to 2 and is a cap that the card can lower, a fixed VRAM reserve is kept for the
desktop, and a request finds its home by its prompt. No header is needed.

**At load** (`limbo_serve_gpu -m <rung 1> --ctx 8192`, no other flag; `--sessions N` caps or raises it, `--sessions 1` disables the second home,
`--vram-reserve-mib N` moves the reserve, default 768). Homes come first, then the checkpoint slots; both leave the reserve free. The decision is
logged with its numbers, and `Service::startup_note()` carries the same text:

    serve: homes: 2 of 2 asked (1913 MiB free before, 222.8 MiB per home, 768 MiB reserve, 1689 MiB free after)
    serve: checkpoints: 8 of 8 asked, 62.8 MiB each (1177 MiB free after)

Where a second home does not fit, the server runs with one and says why (`serve_test` on a fake card with 818 MiB free): `homes: 1 of 2 asked
(... ); running with 1: home 2 needs 100.0 MiB and the 768 MiB reserve, 818 MiB are free`. `--sessions 1` logs `homes: 1 (--sessions 1; a second
would take 222.8 MiB)`: the same server with one home, measured below, `1,413 MiB free after` the slots. With both homes and 8 slots the server's
process holds 14,540 MiB (`nvidia-smi --query-compute-apps`) and the card 830 MiB free, desktop included.

**Routing** (`Service::route`, one rule for every request):

1. a pin wins: `X-Limbo-Session: 1` is home 1; any other value is a label, bound to the home its first request was routed to (a number that is
   not a home is routed like no header);
2. otherwise the home that can reuse the most of the prompt: its whole tape if the prompt extends it, else the newest checkpoint at or before the
   divergence; it only counts if that is more than the opening every conversation of an agent shares (the prompt's first message boundary: the
   system prompt and tools). Reusing more than the opening means a whole message beyond it, or the tape itself; a coincidence of a few tokens never
   counts, and neither does a shared system prompt. Ties: the longer common prefix, then the more recently used;
3. nobody qualifies: the least recently used home (a home never used is the oldest). It is taken over: its tape is cut back to the opening it
   shares with the new prompt (the Root checkpoint, when there is one), its other checkpoints are released, the rest is read.

The first version of rule 2 also demanded 64 reusable tokens; a tiny conversation (a Head checkpoint 27 tokens in) then failed it, fell to rule 3
and took the other conversation's home whenever it had just run. It was dropped for the reason above, and `serve_test` has a case that fails with it.

Per request, `timings.home` says which home served it, and the log line carries `home=<n> via=<only|pin|prefix|lru>`.
