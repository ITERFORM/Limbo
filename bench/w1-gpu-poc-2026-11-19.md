# W1 GPU proof of concept, rung 1 on the RTX 4060 Ti (2026-11-19)

Rung 1 (Qwen3.6-35B-A3B UD-IQ3_XXS, `qwen35moe`) generates greedy tokens on the GPU from Limbo's own
CUDA code and matches the CPU reference (`limbo::step::Ref`): 248 of 248 teacher-forced positions agree on
the top-1 token across three prompts, and free-running 64-token generations are identical to the CPU's
first 32 tokens and to the oracle's 16 tokens on `prose` and `code`. Decode runs at 76 to 80 tok/s.
This is a proof of concept: simple kernels, token-by-token prefill, one sequence, nothing optimised.

## What was built

| file | what |
|---|---|
| `src/cuda/gemv.cu`, `include/limbo/cuda/gemv.hpp` | GEMV `y = W x` over weights in the GGUF block layout (F32, BF16, Q8_0, Q2_K, Q3_K, Q6_K, IQ2_S, IQ3_S, IQ4_XS), the MoE form (expert ids from device memory), the embedding row. One warp per row, 8 elements per lane per 256-element super-block, fixed shuffle tree, fp32 accumulation. Written from the layouts in `limbo/quants.hpp` and the decode math in `src/quants.cpp`; the codebooks are `src/ggml_grids.cpp`'s arrays copied to the device at start, never retyped. |
| `src/cuda/ops.cu`, `src/cuda/ops.hpp` | RMS norm (sum in double, as the reference), depthwise conv + SiLU, q/k L2 norm, the delta-rule scan, gated per-head norm, attention preparation (norm, NEOX partial RoPE, f16 KV write), GQA attention, SwiGLU, router softmax + top-8 + weight handling, shared-expert gate, MoE combine, argmax. |
| `src/cuda/gpu.cu`, `include/limbo/cuda/gpu.hpp` | `limbo::cuda::Gpu`: weights to VRAM once (pinned double-buffered staging from the mmap), per-layer state, and `step(token, pos, head)`: the whole forward pass as one stream of launches with no host round trip inside (the router's top-8 never leaves the device). |
| `tools/gpu_forward.cu` | the parity gate, free-running generation and timing. |
| `tests/cuda_gemv_test.cu` | per-format GEMV test on real rows. |
| `mk/cuda.mk` | `src/cuda/*.cu` -> `liblimbo_cuda.a`, `tests/cuda_*_test.cu`, `tools/gpu_forward`; skipped when there is no nvcc. |

The MTP block (`blk.40`) is not loaded. Every kernel follows `src/step.cpp` op for op, including where it
sums in double and the association of its float products. The GPU mirrors the reference's default
arithmetic (fp32 activations); `Ref::set_oracle_arith` (the opt-in that rounds activations like llama.cpp's
CPU path) is not mirrored.

## Commands

```
nice -n 10 make -j6 BUILD=build-cuda tools test
build-cuda/bin/tests/cuda_gemv_test
nice -n 10 build-cuda/bin/tools/gpu_forward --names hi,prose,code --parity 32 --gen 64 --trace0
nice -n 10 build-cuda/bin/tools/gpu_forward --names prose --parity 20 --gen 0 --trace-pos 74
nice -n 10 build-cuda/bin/tools/gpu_forward --no-cpu --names hi,prose,code --gen 256
```

The model is the rung-1 file named in the task. Before loading, `Gpu::open` calls `cudaMemGetInfo` and
refuses with a message unless at least 14.6 GB are free (`--min-free-gb`); with `--min-free-gb 20` it printed
`gpu_forward: only 16.203645 GB of VRAM free (of 16.806445 GB), need >= 20.000000 GB: the desktop or its engine holds the rest`
and exited 3 before touching the card. One GPU job ran at a time.

(attention and GDN projections, shared experts, embedding, head), Q8_0 (layer 39's attention and shared
expert), IQ2_S (gate/up experts of 39 layers) and IQ3_S (gate/up of one layer, down of 37), IQ4_XS (down of 3
layers). Q2_K, Q3_K and BF16 occur only in the MTP block (`blk.40`), which the forward pass does not load; they
are tested because they are rung 1's formats.

The MoE form: 8 experts chosen by device-side ids (first, last and spread), once with one input shared by
all slots (gate, up) and once with an input per slot (down); 392 to 416 rows per run compared:

## 3. Parity: teacher-forced, GPU against CPU

For each prompt, `Ref` and `Gpu` run the same token sequence: the prompt, then 32 tokens that are the CPU's
own greedy choices. Every position's logits (248,320) are compared. CPU time is `Ref` on 8 threads beside
other jobs. `max|dlogit|` is over the vocabulary; `cpu-gap` is the CPU's top-1 minus top-2 logit.

| prompt | positions | top-1 agreement | on generated positions | max\|dlogit\| worst | median | mean | free-running vs CPU greedy | vs oracle capture |
|---|---|---|---|---|---|---|---|---|
| hi | 2 + 32 | 34/34 | 32/32 | 3.896e-04 | 7.868e-05 | 9.130e-05 | first 32 tokens identical | (rung1-hi.jsonl, 2 tokens): differ first at index 1 |
| prose | 55 + 32 | 87/87 | 32/32 | 1.007e+00 | 4.072e-04 | 3.144e-02 | first 32 tokens identical | (rung1-prose.jsonl, 16 tokens): identical |
| code | 95 + 32 | 127/127 | 32/32 | 1.955e-03 | 3.681e-04 | 4.322e-04 | first 32 tokens identical | (rung1-code.jsonl, 16 tokens): identical |

The whole command was run twice, the second time after the reference's `src/step.cpp` had been edited by
another agent (scan head mapping fixed in code instead of an env switch, the 9th router entry kept for the
trace, an opt-in oracle arithmetic): the per-position tables, the generated ids and the texts are identical
between the two runs (`diff` of the logs), and the decode speed of the second was 76.0, 76.4 and 80.1 tok/s.
The tables below are the first run's.

Top-1 agreement is 248/248. The worst logit difference is 3.9e-4 on `hi` and 2.0e-3 on `code`, below the 1e-2
the task expected from summation order; `prose` has one family of exceptions, explained next.

### Where the 1.0 on `prose` comes from: a router near tie

`prose` positions 74 to 86 show max|dlogit| between 1.3e-2 and 1.0 (position 74: 0.878, 78: 1.007), against a
median of 4e-4. `--trace-pos 74` compares every layer at position 74, including the routed experts. Layers 0 to 25 agree
to 2e-5; at layer 26 the CPU and the GPU pick different experts, because the 8th and 9th router logits are
5.58e-5 apart on the GPU, while the residual stream entering that layer already differs between the two by up to
2.3e-5 (layer 25 below), so a different summation order is enough to reorder them. Everything after is
the consequence of one expert swapped for a near-equal one (gdn state and KV carry it forward to later positions):

## 6. What is not done

- Speed work: no CUDA graph (about 900 launches per token, counted from the code), no fused kernels, no tensor
  cores, no weight repack, and the GEMV decodes with plain byte loads (57% of the card's peak bandwidth). The W1
  gate wants decode of at least 78 tok/s and prefill above llama.cpp's on the same prompt: decode is at that
  line (76 to 80 tok/s measured); prefill is token by token at about 92 tok/s and was not compared with
  llama.cpp's.
- Batching and speculation: one token per step, T = 1 only; no verify windows, no MTP (block 40 is not loaded).
- Paging, homes, checkpoints, host KV: one sequence, a dense f16 KV cache sized at open (`--ctx`, at most 8192).
