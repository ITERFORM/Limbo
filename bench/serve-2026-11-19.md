# Serve: the OpenAI-compatible endpoint (2026-11-19)

`limbo_serve` is an HTTP/1.1 server with `POST /v1/chat/completions` (stream false and true), `GET /v1/models` and
`GET /health`. It renders the model's own `tokenizer.chat_template`, runs a `Backend` one token at a time
(the CPU reference `limbo::step::Ref` today, the GPU forward pass later), and splits the generated text into
`reasoning_content`, `content` and `tool_calls`. Everything below was run on 2026-11-19 on this machine.

## What was built

| file | what |
|---|---|
| `include/limbo/jinja.hpp`, `src/jinja.cpp` | a Jinja-subset interpreter (runs the template as written) and the JSON `Value` type + codec the HTTP layer shares |
| `include/limbo/chat.hpp`, `src/chat.cpp` | `Renderer` (template over an OpenAI conversation), `normalize_messages`, the incremental `OutputParser` and `parse_tool_block` |
| `include/limbo/http.hpp`, `src/http.cpp` | sockets + poll server: deadlines on every read and write, chunked bodies, `Expect: 100-continue`, SSE by chunked transfer, `Conn::yield()` |
| `include/limbo/serve.hpp`, `src/serve.cpp` | `Backend`, `RefBackend`, `Sampler`, `Service` (routing, request validation, prefill, decode, stop sequences, the tape) |
| `tools/limbo_serve.cpp` | the binary: `-m model.gguf --port --ctx --threads ...`, binds 127.0.0.1 unless `--host` says otherwise |
| `scripts/chat_fixtures.py` | extracts the template from the GGUF and renders the goldens with Python jinja2 (HuggingFace's environment) |
| `bench/fixtures/chat/` | `template.jinja` (+ sha256), 28 conversations and 4 error cases (`NN_name.json` + `NN_name.expected.txt`), `jinja_cases.json` (76 interpreter cases) |
| `tests/chat_test.cpp`, `tests/serve_test.cpp` | the two suites below; neither needs a model |

The jinja `Value`/JSON codec lives in `jinja.hpp` because the ownership list had no separate JSON file.

## Chat rendering: byte-exact against Python jinja2

Reference: jinja2 3.1.6, `ImmutableSandboxedEnvironment(trim_blocks=True, lstrip_blocks=True, loopcontrols)` with
HuggingFace's `tojson` (`json.dumps(x, ensure_ascii=False)`: key order kept, `", "` / `": "` separators, no HTML escaping)
and `raise_exception` raising `TemplateError`. That is the environment the Qwen template is written for; jinja2's own builtin
`tojson` (sorted keys, `<` as `\u003c`) would give different bytes for tool definitions.

`chat_test`: 98 checks, 0 failures: all 32 chat fixtures byte for byte (every `expected.txt` identical, every error message
equal), 76 of 76 interpreter cases equal to Python jinja2, JSON round trips and Python float `repr`, 33 output-parser checks (reasoning, content, typed parameters, malformed and cut-off blocks, pieces), the
parse -> re-render round trip (below), UTF-8 helpers.

Output parsing follows the template's own teaching: the generation prompt ends in `<think>\n` (thinking) or `</think>\n\n`
(`enable_thinking` false); the text is `reasoning \n</think>\n\n content [\n\n<tool_call>\n<function=NAME>\n<parameter=KEY>\nVALUE\n</parameter>\n...</function>\n</tool_call>]*`.
Parameter values are typed by the request's tool schema (string stays text; integer, number, boolean, array, object parsed);
with no schema a value that is valid JSON is taken as JSON. One parser serves the streaming and non-streaming paths: the test feeds
a long text in pieces of 1..64 bytes and gets the same message as feeding it whole. The key invariant for the tape holds:
`prompt + generated text + <|im_end|>` is exactly what the template re-renders for that assistant turn (test "roundtrip").

## The tape (what it does and where it stops)

The service keeps the tokens the backend has consumed. A new prompt that starts with all of them continues from that position
(`usage.prompt_tokens_details.cached_tokens`, `timings.cache_n`); anything else resets the backend and re-reads. Nothing is
shifted, rewound or rewritten, and the backend sees positions 0,1,2,... consecutively (tested).

Measured consequences, all in `serve_test` and in the live smoke below:

1. A tool-call round (user -> assistant `tool_calls` -> tool result -> next request) reuses 100% of the previous turn, because the
   template keeps the think block of assistant turns after the last user query.
2. A **new user turn** with the template's defaults does not: it drops the think blocks of earlier assistant turns, so the prompt
   diverges from the tape at the first earlier assistant message and the whole prompt is re-read. With
   `chat_template_kwargs: {"preserve_thinking": true}` the template keeps them and the tape is a prefix again (live: 26 of 26).
   Which policy Ariadne wants is the operator's call; the server does not change the template's default.
3. Sending the same request twice re-reads it (the prompt is shorter than the tape; GDN state cannot be rewound without
   checkpoints, PLAN.md section 3.4). Live smoke request 2 shows it: `cached_tokens: 0`.

## Open

- Prefix reuse is whole-tape only: no rewind or partial reuse, one session. A second conversation (Ariadne's sidekick) evicts the
  first. This is what homes + recurrent checkpoints (PLAN.md section 3.4) are for; `Backend` will need a checkpoint/restore or a
  home-select call, and `Service` a table of tapes.
- The template's default drops old think blocks, so every new user turn re-reads the prompt unless the harness sends
  `preserve_thinking: true`. Decision for the operator (context grows when kept).
- Completions run one at a time (single thread, no mutex by design). `/health` and `/v1/models` are answered during a
  completion; other requests wait in arrival order. A client cannot cancel a parked request except by closing its socket.
- Not implemented: `tool_choice` `required` / a named function (treated as `auto`), `n` > 1 (400), logprobs, penalties
  (presence, frequency, repeat), `response_format`/grammar. Unknown request fields are ignored.
- Streaming tool calls arrive as one complete call per delta, not as argument fragments.
- Untyped tool parameters (no schema, or `anyOf`) are guessed: valid JSON becomes JSON, so a string parameter that looks like a number
  is mis-typed unless the schema says `string`.
- `completion_tokens` counts every sampled token including the end token. Generation stops on the vocabulary's eos plus
  `<|im_end|>` and `<|endoftext|>`; other control tokens are printed as text.
- The rendered prompt is tokenized with special parsing on, so a user message containing a literal `<|im_start|>` becomes the
  control token (the same as llama.cpp's server); nothing escapes it.
- Interpreter limits: ints beyond int64 become doubles, `lower`/`upper`/`title` are ASCII only, there is no tuple type
  (`(1, 2)` is a list and prints with brackets), `include`/`import`/`extends`/`call`/`filter`/`raw` blocks are rejected at startup with a
  message naming the construct. Python's `str()` forms are kept where a template can see them (`True`, `None`, `1e-07`).
- `tojson` follows HuggingFace's override. Whether llama.cpp's own jinja engine renders tool definitions with identical bytes was
  not measured here.
- Sampler: temperature first, then top_k, top_p, min_p (the HF/vLLM order); llama.cpp applies truncation before temperature, which
  differs for temperature != 1. Defaults are OpenAI's (temperature 1, nothing else); `--temperature/--top-k/--top-p/--min-p`
  change them.
- Not run: Ariadne end to end, the GPU backend, any speculation. CPU reference speed here was about 0.4-0.5 tokens/s while the machine
  was loaded.
