## What the numbers say about the plan

1. **The DDR lane is cheaper than the specs assumed.** `donors/kv-streaming.md` §9 prices host KV at an
   assumed ~35 GB/s; the box does **47.0 GB/s** at four threads (dual-channel DDR4-3200's ceiling is
   51.2). Four threads is the peak, eight is worse (SMT contention), and both CCXs read at the same
   rate. The KV row rule should therefore be re-fitted upward from ~10 rows: the CPU lane is ~34%
   cheaper than the estimate that produced it.
2. **Write-combined pinned memory buys nothing, and costs nothing.** 6.51 vs 6.54 GB/s is noise, so
   PLAN §3.2's choice of *cacheable* pinned memory is free — it can be read by the CPU lane without
   giving up any transfer rate.
3. **Zero-copy mapped pulls are a trap.** Alone, an in-kernel pull over the link reaches 6.5 GB/s;
   beside a busy GPU it collapses to **1.85 GB/s** (28% of the link) because the reads contend with the
   SMs for memory. The copy engine keeps 6.62 GB/s with the GPU saturated. The engine must move bytes
   with the copy engine and leave mapped pointers to the doorbell path.
4. **The doorbell is not the constraint: 1.34 µs.** The §7 target of ≤50 µs per layer is met 37x over,
   so the split-decode design can afford one hand-off per layer, and the 128-layer round trip (~170 µs)
   is small beside a step.
5. **The CPU lane only pays as parallelism, not as a replacement for a copy.** A 256-token q8_0 KV page
   is 69.6 KB of K+V, which the copy engine moves in ~10.5 µs at 6.6 GB/s. Decoding that page on the
   CPU costs 13.4 µs for one query row and 30.2 µs for four (one KV head's worth of GQA sharing), on one
   core, with the copy engine idle. So the CPU lane does not win the latency comparison at decode; it
   wins only when it runs *while* the GPU is busy — which is exactly what the three-lane design is for,
   but it means the planner must price the CPU lane as added parallelism (a share of the step) and not
   as a cheaper way to read a page.
6. **DMA interference is real but modest; the launch tail is not.** DDR loses ~9% beside a DMA loop
   (42.5 → 38.7 GB/s). Launch+sync is 6.8 µs idle and 8.6 µs median under DDR saturation — but its p99
   is **133.7 µs**, 15x the median. A whole-step graph must not have a launch on the critical path of
   every layer, or that tail is the step's tail.
7. **The pinned tier does not get 2 MiB pages from madvise+populate on this box.** `AnonHugePages`
   backing the region was **0.000 MiB** with THP policy `[madvise]`, so the 4 KiB/2 MiB chase comparison
   is vacuous (0.99x) and PLAN §3.2's "backed by 2 MiB anonymous pages" is unverified. Getting it needs
   explicit hugetlb (`/proc/sys/vm/nr_hugepages`, currently 0) or a khugepaged collapse after the
   region is faulted — the second is the only one that works without root. The single-threaded chase
   also shows no benefit to chase, so this is a *not-yet-measurable* item, not a proven win.
8. **The file tier is a SATA 860 EVO behind btrfs with `compress=zstd:3`, and swap shares the device**
   (`/dev/sdc3`, 3.7 GB in use). 10.8k random-4K IOPS and 3.9k random-64K IOPS (256 MB/s) is the whole
   budget for packs, PLE rows and saved openings; 499 MB/s sequential is what a pack preload can have.
   Compression means a *compressible* payload (zeros, repeated bytes) reads far faster than these
   numbers — and, worse, that a 30%-of-busy-time cold-re-read figure like Strata's is not comparable
   across payload types.

## Four measurement defects this session found and fixed

Recorded because each one produced a *plausible* number that was wrong, and the next person to touch
the probe should know where the traps are:

1. **Item 8, first version** compared a "GB/s" figure over 64 bytes per page: 65,536 touches against
   128. The metric, not the machine, produced the difference. Replaced with ns per touch.
2. **Item 8, second version** had a 4 MiB touched footprint — one cache line per page over 256 MiB —
   which fits in one core's 4 MiB L2, so it measured L2 residency, not the TLB. Replaced with a
   dependent-load pointer chase over 4 GiB, where nothing can be prefetched.
3. **Item 8, final version** then needed its own check: `AnonHugePages` showed the "2 MiB" run was
   backed by 4 KiB pages, which makes the comparison vacuous. The probe now prints that number instead
   of leaving the reader to assume.
4. **Item 9, first version** wrote 512 MiB of a repeated byte, which btrfs compressed away; the read
   came out of RAM as fast as the CPU could decompress, reporting 1278 MB/s sequential and 520k random
   4 KiB IOPS on a SATA drive whose link tops out near 550 MB/s. Fixed with an incompressible PRNG
   pattern plus `POSIX_FADV_DONTNEED` before each read phase; the numbers above are the corrected ones.
