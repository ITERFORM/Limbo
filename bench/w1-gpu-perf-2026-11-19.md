# W1 GPU gate, rung 1: batched prefill and graph decode (2026-11-19)

Rung 1 (Qwen3.6-35B-A3B UD-IQ3_XXS, `qwen35moe`) on the RTX 4060 Ti, Limbo's own CUDA code. This follows
`bench/w1-gpu-poc-2026-11-19.md` (decode 76-80 tok/s, prefill 92 tok/s token by token, ~900 launches per
token). Two things were added to `limbo::cuda::Gpu`: `prefill()`, a batched pass over a chunk of prompt tokens,
and a captured CUDA graph for `step()`. Everything below was run by the commands in the last section, one GPU
job at a time under `build/gpu.lock`.

## Result in one table

All numbers measured on a quiet machine (no CPU job beside the GPU job: a CPU reference run beside it costs 5 to
10 percent of prefill speed, noted where it mattered). llama.cpp is the incumbent of section 1.

| | llama.cpp | Limbo before (PoC) | Limbo now, `planes = 3` (default, exact) | Limbo now, `planes = 2` (opt-in) |
|---|---|---|---|---|
| prefill pp512 | 2260.98 ± 78.28 | 92 (token by token) | 1943 (chunk 1024) | 2474 (chunk 1024) |
| prefill pp2048 | 2078.44 ± 134.32 | 92 | 2085 (chunk 1024), 2179 (chunk 2048) | 2695 (chunk 1024), 2800 (chunk 2048) |
| decode tg128 | 75.99 ± 1.22 | 76 to 80 | 91.0 (CUDA graph) | same |

- **The speed gate is met with `planes = 2`** (pp512 +9%, pp2048 +30% to +35%) and **with `planes = 3` at 2048 tokens**
  (chunk 1024: +0.3%, inside llama.cpp's own spread; chunk 2048: +5%). **`planes = 3` is 14% short at 512 tokens.**
- `planes = 3` is the default because PLAN.md §3.3 allows nothing lossy by default: every product is within 3e-7 of
  the exact one. `planes = 2` (1 part in 16192 per activation block) is faster by a factor 1.27 and moves router
  near-ties more often (section 5.3), so it is an explicit `set_prefill(2, ...)`.
- Decode passes llama.cpp's tg128 by 20% and the 78 tok/s gate. The captured graph is worth +4 to +8 tok/s of it (the kernel-by-kernel runs are noisier);
  most of the rest is the delta-net scan kernel (1.40 to 0.39 ms per token) and the other fixes of §2.
- Parity (section 5): on the three oracle prompts every mode keeps the top-1 token and `planes = 2` and `3` keep
  the 32-token greedy continuation of the CPU reference, free-running generation after a batched prefill matches
  the CPU's first 32 tokens and the oracle capture on all three. Beyond a few hundred tokens the logits of
  *any* two implementations drift apart through router near-ties (the CPU reference against the GPU's own
  token-by-token path: max|dlogit| 2.17 at 512 tokens); that is an open item, not something this work introduced.

### Prefill design (donor ideas: `docs/donors/kindi.md` §2.3, §2.5, §2.6, §2.7)

- **Weights are integers times a group scale.** Every format the forward pass uses decodes to |q| <= 127 and one
  fp32 scale per 16 or 32 columns (format facts of `limbo/quants.hpp`). A weight tile is decoded once and applied
  to every token row of the tile on the int8 tensor cores; the int32 accumulator starts at 0x4B400000 so one
  FADD turns it into a float (kindi §2.3).
- **The activations are the only rounded quantity, and the rounding is a dial.** `act_quant` cuts each row into
  blocks of 32, takes the block amplitude as an integer of R levels (R = 127, 16192 or 2,000,000) and splits it
  into `planes` balanced base-128 digits, one int8 plane each. 1 plane is a plain Q8 activation, the arithmetic of
  llama.cpp's own kernels. 2 planes resolve a block's amplitude to 1 part in 16192, 3 planes to 1 in 2e6 (fp32
  like). The planes go through the tensor cores separately and are recombined in fp32 per group.
- **Dense tile:** 128 weight rows x 64 token rows (32 with 3 planes, where the register file runs out), K in
  stages of 128 columns.
- **MoE tile (the decode of the weights is the cost, not the products):** a warp owns its weight rows, stages the
  raw block bytes with wide `cp.async` copies (double buffered), and each thread decodes only the 4-byte pieces
  of the A fragments it holds, straight from shared memory. IQ2_S's grid is held as byte-permute selectors (4 KB
  instead of 8) and signs are applied four bytes at a time. Experts with up to 32 pairs use tiles of 16 tokens,
  busier ones tiles of 32. The generic tile of the dense kernel did this in 2.64 ms per layer for gate+up at 512
  tokens; this one in 1.3 ms.
- **Delta net:** conv over the chunk is parallel over (token, channel); the recurrence is one kernel per value
  head, one thread per value column holding its 128 state values in registers, running the tokens in order with
  the decode kernel's arithmetic statement for statement.
- **Attention:** one warp per (query head, 16 queries), keys in blocks of 64, online softmax. Q K^T and P V run on
  fp16 `mma` with fp32 accumulation; K and V are the cache's own f16 (exact), Q and P are split into hi + lo
  halves (22 bits), so the products are fp32-accurate. V is stored transposed in the cache ([kv head][dim][pos])
  so a B fragment of P V is one 8-byte load; the contraction order inside an mma is chosen so the C layout of two
  S tiles is already the A fragment of P V (no shuffles).
- **Head only on the last token** (kindi §2.7): the final norm and the LM head run once, on the chunk's last row.
- **Two streams:** the delta net's `z` product runs beside its scan chain (the scan is latency bound, 32 blocks).
- **Small kernels:** warp-per-row norms (the double-precision `sqrt` was a visible cost when every thread did
  it), a RoPE cos/sin table per chunk instead of `pow`/`sincos` in double per element.

### Decode design

- `step()` is captured as a CUDA graph: token and position live in device memory (`d_args`), staged through a
  ring of 256 pinned slots, so one graph replays every position; two graphs (with and without the head). The
  first pass of each variant runs eagerly so every module is loaded before capture.
- The delta-net decode scan keeps its column in registers (the loop had one dependent global load per iteration:
  1.40 ms/step to 0.40), the norms compute their double `sqrt` once per block, and the alpha/beta and the
  shared expert's gate/up are single launches, the shared expert's SwiGLU is formed in shared memory inside the
  down product.

kernel error. Chunking does not change a bit of it (chunk 128 and chunk 1024 gave the same 2.220).

## 7. Open

1. **Exact-mode prefill is 14% short of llama.cpp at 512 tokens** (1943 vs 2261). The 3-plane MoE gate/up kernel
   needs 56 KB of shared memory, so one block per SM (77 ms against 54 ms with 2 planes), and the dense products
   spend more issue slots recombining planes than the tensor cores spend multiplying (16-wide weight groups: Q6_K,
   IQ2_S). Ideas: stage the activation planes by half super-block, a fragment-direct kernel for Q6_K, an int
   chain that folds two planes inside the accumulator where the range allows (Q6_K only).
2. **Long-context parity needs an oracle.** The checks above show that logits at 500+ tokens are not a usable
   comparison between any two implementations; token-exactness should be judged on greedy tokens against
   llama.cpp captures of long prompts (`oracle/` holds only 16-token captures of short prompts).
3. The delta-net scan is 16.5 ms of 264 (a dependent chain of 128 FMAs per token and column, bit-identical to
   decode by design); a chunkwise-parallel rule would not be bit-exact.
4. Decode is at about 63% of the memory floor: the GEMVs read quant blocks byte by byte (150 to 210 GB/s); the raw-staging
   of the MoE prefill kernel would apply, and the 900 kernels could shrink further (norms, top-k, combine).
5. The VRAM cost of the batched path is about 0.35 MB per chunk token (0.36 GB at the default chunk of 1024,
   0.7 GB at 2048), allocated at the first batched prefill; the card has 1.9 GB free at the default.
6. `planes = 1` is not offered as a mode to use: it loses the greedy continuation of `code`.
